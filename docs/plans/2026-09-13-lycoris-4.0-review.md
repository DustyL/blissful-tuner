# LyCORIS 4.0.0 review — is there anything worth integrating?

**Date:** 2026-09-13  **Scope:** `~/LyCORIS` `b4d2f5e..4a6a333` (last pre-4.0 upstream merge → HEAD,
148 files, +15,055/−547), against blissful-tuner `33152af8`.
**Verdict:** nothing to port. The 4.0 kernels arrive by import (LyCORIS is editable in `venv314`,
already at 4.0.0), and **in the production DLAY LoKr recipe they are inert by design** — under
`compile = true` LyCORIS hands the eager body to Inductor, which then beats its own Triton kernels
at Wan shapes on both time and memory. Four small blissful-side follow-ups came out of the review
(§5), none of them kernel work.

## 1. What 4.0 is

Fused Triton/TileLang kernels behind every algorithm (`lycoris/kernels/`), chosen per call by
`lycoris.kernels.select.choose()` in the order `triton > tilelang > compile > torch`, with the stock
PyTorch body as the always-available fallback. Signatures are unchanged; `lycoris.kohya.create_network`
(what `src/musubi_tuner/networks/lycoris.py` calls) is untouched apart from `exclude_name` support.
Two smaller items rode along: `exclude_name` is now honoured inside a matched block (`2fc7c60`), and
the LoKr conv bypass chain was repaired (`ff4a594`, #221 — conv-only, blissful passes `conv_dim=0`).

Verified on this box: `python -m pytest test/kernels test/torch_compile.py` → **53 passed** in
`venv314` (torch `2.15.0a0+gitd068017`, triton `3.8.0`, RTX 5090). Needed `pip install parameterized`
(test-only dep, now in `venv314`). `available_backends()` → `('triton', 'compile', 'torch')` — no
TileLang installed, none needed.

## 2. How blissful reaches LyCORIS

Two paths use the library, both through the bridge in `src/musubi_tuner/networks/lycoris.py`:

- **Training:** `network_module = "networks.lycoris"` → `lycoris.kohya.create_network`. All three DLAY
  LoKr configs (`configs/dlay_lokr_*.toml`) use it with `algo=lokr`, `full_matrix=True`, `dora_wd=True`,
  `wd_on_output=True`, `preset=attn-mlp`, `conv_dim=0`, `compile = true`, no block swap, fp16. They
  point at `/root/...` (the B300 / `~/blissful-tuner-remote`); the conclusion below depends on the
  *wrapping* (`compile=true`, no block swap), not on which box runs it or which LyCORIS build it has.
- **Inference:** `--prefer_lycoris` → `create_network_from_weights` → `merge_to`. This runs outside any
  `torch.compile`, and `_prepare_merge_context` moves the adapter onto the base weight's device
  (`modules/base.py:495`), so on a CUDA-resident model the merge *does* take the Triton `kron_weight`
  and `weight_decompose` kernels. See §4.

The native `networks.lokr` / `networks.loha` modules are separate implementations and never import
LyCORIS; the kernels cannot reach them.

The dispatch decision that settles the question is in `lycoris/kernels/select.py`:

```python
def choose(tensors, supported=True, backend=None):
    if torch.compiler.is_compiling():
        return "torch"          # b42d907 "make kernel dispatch torch.compile safe"
```

`LycorisBaseModule.apply_to()` does `module.forward = self.forward` (`modules/base.py:358`), and
blissful applies the network (`trainer_base.py:1806`) **before** compiling each block
(`trainer_base.py:1916` → `model_utils.compile_transformer`). So under `compile = true` the whole
LoKr forward is traced inside blissful's compiled block, `is_compiling()` is true, and every call
takes the `torch` tier. The only way a kernel fires inside a compiled block is
`disable_linear_from_compile`, which runs iff `blocks_to_swap > 0 and not allow_linear_for_compile`
(`wan_train_network.py:694`) — off in every DLAY LoKr config.

## 3. Measured on the 5090 (receipts)

Stand-in block = two Wan 2.2 14B Linears (5120→5120 q, 5120→13824 ffn) + residual + GELU, fp16 frozen
base, fp32 adapter, `autocast(fp16)`, 4096 tokens × batch 1, fwd+bwd wall over 60 iters after 20 warmup,
one process per row. Adapter = the DLAY `network_args` above (dim 64 / alpha 32 / full_matrix / dora_wd).
`picks` is what `choose()` returned on the first forward. Script:
`scratchpad/lycoris4_probe.py` (reproducible from the description; not committed).

| mode | wrapping | `LYCORIS_KERNEL_BACKEND` | picks | ms/it | peak MiB |
| --- | --- | --- | --- | ---: | ---: |
| rebuild + DoRA (**production math**) | eager | torch | torch | 25.90 | 1703 |
| rebuild + DoRA | eager | auto | **triton** | 21.18 | 1410 |
| rebuild + DoRA | **compiled block (production)** | torch | torch@compiling | **17.04** | **765** |
| rebuild + DoRA | **compiled block (production)** | auto | torch@compiling | **17.04** | **765** |
| rebuild + DoRA | compiled, Linear dynamo-disabled (= block swap) | torch | torch | 25.92 | 1703 |
| rebuild + DoRA | compiled, Linear dynamo-disabled | auto | **triton** | 21.21 | 1450 |
| bypass (no DoRA) | eager | torch | torch | 9.74 | 906 |
| bypass (no DoRA) | eager | auto | **triton** | 17.17 | 670 |
| bypass (no DoRA) | compiled block | torch / auto | torch@compiling | 7.9 | — |

Three readings:

1. **Production is unaffected and already the best row.** Both backends give 17.04 ms / 765 MiB under
   `compile = true`, because neither runs a kernel. Reaching the Triton path (exclude Linears from
   compile, as block swap does) costs **+24 % time and +1.85× peak memory** versus the compiled body.
   Inductor fuses the rebuild chain better than the hand-written merge kernel at these shapes — the
   same conclusion LyCORIS's own table reaches for `lokr` merge (`0.93× dev / 0.89× fb vs compile`,
   `docs/kernels/benchmarks.md`).
2. **The LoKr bypass kernel loses to eager at Wan full-matrix shapes** — 1.75× slower at 4096 tokens,
   1.7× at 8192, tuner on or off (`LYCORIS_KERNEL_TUNE=off` changes nothing). LyCORIS's 4.26× bypass
   figure is a 4090 sweep over rank-factored ≤11008×4096 shapes; with `full_matrix=True` the
   Kronecker factors are (80,64)/(80,64) and (128,108) — inside the kernel's `MAX_KRON_FACTOR = 128`
   cap, so the kernel *does* run, it is just slower than cuBLAS on the eager grouped chain. It does
   save ~240 MiB per block pair, which is not a lever anyone needs on the B300.
3. **Bypass mode itself is 2.15× faster than rebuild (7.9 vs 17.0 ms compiled)** — but that is a
   pre-4.0 lever, not a 4.0 one, and it is not free: `LokrModule.bypass_forward` has **no DoRA
   branch** (`modules/lokr.py:557`; `wd` is only applied in `_rebuild_forward`, `:565`), and
   `kohya.create_network` has no guard, so `bypass_mode=True` + `dora_wd=True` **silently drops DoRA**.
   If DoRA-on-LoKr is ever judged not to be earning its 2× (cf. the DoRA×Prodigy inertness findings
   in `memory/project_dora_prodigy_param_group_fix.md`), `bypass_mode=True` without `dora_wd` is the
   recipe change — and it should be a deliberate A/B on samples, not a side effect of this update.

## 4. Numerics and reproducibility

- When a kernel *does* engage (eager LoKr, or any run with block swap), the arithmetic order changes
  — LyCORIS calls that out as the reason for the major bump. `docs/kernels/precision.md` reports the
  fused error at or below eager (fp32 accumulation) and that deliberate intermediate roundings mirror
  the eager chain, so it is not a precision loss, but it is a different run.
  **For any A/B against a pre-4.0 LoKr run that used block swap or `compile=false`, pin
  `LYCORIS_KERNEL_BACKEND=torch`.** For the compiled DLAY recipe nothing changed and no pin is needed.
- **`--prefer_lycoris` merges on CUDA now go through the Triton merge kernels** (`kron_weight`, and
  `weight_decompose` for `dora_wd` adapters), so merged inference weights differ from pre-4.0 at the
  ULP level. Pin `LYCORIS_KERNEL_BACKEND=torch` for bit-parity against a pre-4.0 merged output;
  otherwise it is a wash (§4 precision numbers). The native merge path (`merge_nonlora_to_model`,
  the default) is unaffected.
- First use of each (op, shape, dtype) on a device runs the measured tile tuner and writes
  `~/.cache/lycoris_kernels/tuning.json`; expect a slightly longer first step on a fresh machine
  when kernels are reachable.
- Unchanged in 4.0 and still true: `rank_dropout` builds its mask with `torch.rand(weight.size(0))`
  on CPU (`modules/lokr.py:374`), so the config comment "rank_dropout removed — incompatible with
  torch.compile" stands. The DyLoRA compile fix in `b42d907` does not touch it.
- Unchanged and worth knowing for `dlay_lokr_prodigy_training_full.toml`: with `full_matrix=True`
  both Kronecker halves are full, and `LokrModule.__init__` then forces `alpha = lora_dim`
  (`modules/lokr.py:210-212`) → `scale = 1`. **`network_dim = 64` / `network_alpha = 32` are both
  ignored in that config.** Cosmetic, but the comment block above them reads as if they matter.

## 5. Blissful-side follow-ups found during the review

None of these is 4.0 integration; they are what turned up while tracing the two LoKr paths.

| # | Finding | Where | Severity | Fix |
| --- | --- | --- | --- | --- |
| 1 | **Native `networks.lokr` starts with a non-zero random ΔW when w2 goes full-matrix.** `LoKrModule.__init__` kaiming-inits `lokr_w2` (`lokr.py:122`); LyCORIS `weight_gen` zero-inits it (`functional/lokr.py:113`). Full w2 is selected when `lora_dim ≥ max(out_k, in_n)` — for Wan 5120² with `factor=-1` that is `dim ≥ 64`. Measured: dim 64 / alpha 32 gives a step-0 delta with mean magnitude **25 % of the base weight** on every targeted Linear (1 % at alpha 1). Native LoHa is fine (`zeros_(hada_w1_a)`). No DLAY config uses `networks.lokr`; nothing shipped is affected. `tests/test_lokr_factor_roundtrip.py` has no zero-init assertion. | `src/musubi_tuner/networks/lokr.py:122` | real bug, unshipped path | `nn.init.zeros_(self.lokr_w2)` + a test asserting `get_weight()` is all-zero for both branches |
| 2 | **`--fp8_scaled` base + `networks.lycoris` is unguarded and would corrupt.** LyCORIS's fp8 handling keys on `__class__.__name__ == "Fp8Linear"` with a `weight_scale` attr (`modules/base.py:17-24`); blissful's fp8-scaled Linears stay `nn.Linear` with `scale_weight`. fp8 patching happens inside `load_transformer` (`load_wan_model` → `apply_fp8_monkey_patch`, `wan/modules/model.py:1319`), i.e. *before* `apply_to`, so `_current_weight()` returns the raw unscaled fp8 tensor and `_rebuild_forward` does `base_weight + diff_weight.to(fp8)` — float8 add is unimplemented in torch, so this most likely raises, and if it ever doesn't it merges an unscaled weight. Fails or corrupts; either way unguarded. ConvRot already has this guard (`krea2_train_network.py:166`); fp8 does not. *Code-read, not executed* (my quick harness mis-built the fp8 module). | `src/musubi_tuner/networks/lycoris.py` `create_network` | latent hazard, no current config hits it | raise unless `bypass_mode=True` and not `dora_wd`, mirroring the ConvRot guard |
| 3 | **Run logs do not record which LyCORIS arithmetic was used.** Now that the same config can run eager-torch, Inductor or Triton depending on wrapping, reproducibility wants `lycoris.__version__` and `resolve_backend()` in the startup log. | `src/musubi_tuner/networks/lycoris.py` | reproducibility | two `logger.info` lines in `create_network` |
| 4 | **`docs/loha_lokr.md` should say the above.** `LYCORIS_KERNEL_BACKEND`, "inert under `compile=true`", the bypass/DoRA exclusivity, and the `full_matrix` alpha note. | `docs/loha_lokr.md` | docs | one short section |

Not recommended: porting Triton kernels into blissful (they arrive by import), routing native
`lokr.py` through `lycoris.functional` (it exists to avoid the dependency), or re-running the
LyCORIS bench suite generically — only a production-shape measurement answers the question, and it
has been run.

## 6. Open gate

A real 14B LoKr A/B was not run (ComfyUI holds 26 GB of the 5090; the DLAY LoKr configs target the
B300). Given §3 it is not needed to reach the verdict: the production wrapping cannot execute a
kernel, so the only quantity that could change is zero. If block swap is ever added to a LoKr
recipe, that run *would* engage Triton for every swapped block's Linears — measure it then, with
`LYCORIS_KERNEL_BACKEND=torch` as the control.
